# 核心運作概念
翻譯者提交翻譯到Github repo，觸發Cloudflare的build script，解讀repo檔案結構，算出所有網頁，更新網站

## build script
1. 解讀`content/`的檔案結構(特定格式的目錄、`.md`內容檔案)，算出所有資料和和關聯關係
2. 根據所有資料和和關聯關係，渲染所有頁面的`.html`檔案到`dist/`，頁面的`.html`檔案相對於`dist/`的路徑，就是使用者存取該頁面的URL

## content/ 翻譯者的工作區
```
/content/                                 
    /translators/{translator_id}/                        翻譯者的翻譯作品空間。建議用自己的 GitHub 帳號，像是：kerrrr111
        description.md                             翻譯者。
        {可讀標題}.md                               翻譯者的翻譯作品。建議用可讀標題，像是：hashire-merosu.md

    /works/
        {可讀標題}.md                               作品。建議用可讀標題，像是：kokoro.md

    /source-authors/
        {可讀人名}.md                               作者。建議用可讀人名，像是：dazai-osamu.md

    /source-translators/
        {可讀人名}.md                               中間翻譯者。多層翻譯鏈才需要，如法文原作經英譯再中譯。建議用可讀人名，像是：yamada-taro.md
```
## dist/ 整個網站的所有網頁
```
/translations/{id}/index.html                       某篇翻譯作品的頁面
/works/index.html                                   所有作品的頁面
/works/{id}/index.html                              某個作品的頁面
/tags/{tag}/index.html                              擁有某標籤的所有作品頁面
/translators/{id}/index.html                        某個翻譯者的頁面
/source-authors/{id}/index.html                     某個原作者的頁面 
/source-translators/{id}/index.html                 某個中間譯者的頁面 

/translations.json                                  全站翻譯作品索引，前端搜尋/篩選用

```

# 核心設計原則

1. **看得見的名字只負責給人看，不承擔身分辨識**
   
   `content/`內目錄、檔案名稱一律是給翻譯者看的可讀提示(書名、作者名等)，真正的id是的內容檔案內的 `uuid` 。
   
    由建立該檔案的人在本機用 `crypto.randomUUID()` 產生，不需要中心化協調，可以多人分散式 PR 提交。若身分靠流水號或人工命名收斂，需要中心化協調，會有撞號、merge 時要重新計算的問題，UUID 可以繞開這個問題。
    
   目錄名稱、檔案名稱一律是給人類瀏覽用的可讀提示(書名、作者名等)，可以隨時補充資訊讓它更好辨識(例如書名不夠獨特就加作者名)，完全不要求全站唯一、不要求彼此收斂，也不參與任何比對邏輯。真正的身分識別碼固定放在檔案內容(frontmatter)裡的 `uuid` 欄位，

   例外:`/content/translators/{譯者id}/` 這一層目錄名稱本身就是識別碼(建議採 GitHub 帳號，先到先得)——因為它是本站帳號，git 路徑本身就天然防止兩人佔用同一個名字，不存在「不同人各自命名、卻指向同一個真實世界實體」的分裂風險，不適用上述分離，不需要額外的 uuid 機制。

2. **判斷「是不是同一個實體」，依賴外部 ID，不依賴名字**
   `works`、`source-authors`、`source-translators` 這三種——會被不只一個、彼此不知情的貢獻者各自嘗試登記——build 時比對是否重複，優先順序是:`wikidata_id` 相同 → 判定重複;沒有 `wikidata_id` 時，退而比對從 `editions[].url`(works)或 `source_url`(source-authors/source-translators)解析出的青空文庫/古騰堡站方編號是否相同 → 判定候選重複;兩者都沒有 → 無法自動判斷，依賴翻譯輔助工具的搜尋功能與事後的社群巡邏彌補。詳見第 6 節。

3. **身分只存一份，不在多處重複填寫**
   凡是已經能從別處推得的資訊，不再要求於檔案內容中重複填寫——避免兩處各自更動後彼此不同步的風險。這條原則除了適用於識別碼本身，也適用於「屬於作品的事實」:作者、原文語言、tags、category 這些不會因為譯者不同而不同的事實，一律只存在該作品自己的檔案裡一份，`{uuid}.md` 透過 `work_id` 反查取得，不重複填寫。實體之間用「引用」欄位(`work_id`、`author_id`)串接，一律引用對方的 `uuid`，不用巢狀存放。

- **URL 設計原則**:只做 build 時就窮舉產生的靜態單一資源 URL(如 `/translations/{uuid}/`、`/works/{uuid}/`)，不做動態多條件查詢組合(`?tag=X&sort=Y` 這類改用前端 JS 記憶體 filter，不對應獨立網址)，不做 HTTP 寫入動詞——寫入操作一律走 GitHub PR 流程。公開網址一律採用 `uuid`，不採用可讀前綴——現代社群平台/通訊軟體多半會解析網頁 meta 資訊、顯示成標題+摘要+縮圖的預覽卡片，退一步網頁本身也能用連結文字包住網址，網址字串本身好不好讀並不重要，重要的是它一旦被引用就永久不變，不會因為檔案事後改名而斷連結。

## 2. Repo 原始碼結構

Repo 根目錄分四塊，依「誰會去動它」分開，彼此不混:

```
/docs/                                    ← 規格與指南文件(本文件所在處)

/content/                                 ← 譯者實際會碰的地方，詳見下方

/scripts/                                 ← Node.js build script 本體(讀 content/，產生靜態頁面)，跑在 Node，不出現在瀏覽器裡

/assets/                                  ← 依附在輸出 html 上、跑在瀏覽器端的 JS/CSS(hover 顯示註解、filter 搜尋等)
    js/
    css/

/CONTRIBUTING.md
/LICENSE
```

`content/`、`scripts/`、`assets/` 三者職責不重疊:`content/` 是純資料(給 build script 讀)，`scripts/` 是產生網站的邏輯(build 時跑一次，不出現在最終網頁裡)，`assets/` 是網站本身的前端資源(不參與 build 邏輯，只是被複製/打包進輸出)。三者是平行關係，不互相巢狀。

**為什麼 `works`/`source-authors`/`source-translators` 拿掉目錄包裝，`translators` 沒有**:前三者從頭到尾只有一份內容，目錄對它們來說純粹是不必要的包裝。`translators/{id}/` 底下真的裝了不只一種東西——自己的 profile 加上任意數量的譯文——是真正的一對多容器，才需要目錄撐住這個關係。

**新增時機**:`content/works/`、`content/source-authors/`、`content/source-translators/` 底下的檔案，由第一個需要引用該實體、卻在既有清單中找不到對應項目的譯者，在同一個 PR 中一併新增(見翻譯者指南)。沒有「事先建好資料庫」這回事——這個架構沒有後端，PR 是唯一的寫入機制。

# 內容檔案規格


| 身分 | 路徑 | id來源 |
|---|---|---|
| 翻譯者 | `/content/translators/{translator_id}/description.md` | id是目錄名稱 |
| 作品 | `/content/works/{可讀前綴}.md` | id是內容檔案的 `uuid` 欄位 |
| 作者 | `/content/source-authors/{可讀前綴}.md` | id是內容檔案的 `uuid` 欄位 |
| 中間翻譯者 | `/content/source-translators/{可讀前綴}.md` | id是內容檔案的 `uuid` 欄位 |

## 翻譯者
位置：`/content/translators/{譯者id}/description.md`

| 欄位 | 必填 | 說明 |
|---|---|---|
| `display_name` | 選填 | 顯示名稱，不填則顯示目錄名稱 |
| `bio` | 選填 | 自我介紹 |
| `links` | 選填 | 外部連結陣列(個人網站、其他社群帳號等)，逗號分隔 |

整份檔案可以不存在，沒有時，翻譯者頁面只顯示譯者id與作品列表，不擋 build。

## 作品
位置：`/content/works/{可讀標題}.md`
用內容檔案內部的`uuid`當作身分，檔案名稱可以隨時改，不影響任何引用。

| 欄位 | 必填 | 說明 |
|---|---|---|
| `uuid` | **必填** | 作品的身分，建立檔案時本機用 `crypto.randomUUID()` 產生，永遠不會修改|
| `wikidata_id` | 選填(建議) | 作品的 Wikidata QID，若存在則 build 時自動抓取多語言標題等資料，也是跨檔重複偵測的主要依據(見第 6 節) |
| `title` | 有 wikidata_id 則選填，否則必填 | 標題(至少一種語言)，做為 Wikidata 抓取失敗時的 fallback |
| `author_id` | 必填 | 指向 `/content/source-authors/{id}/` |
| `original_language` | 必填 | 原作最初寫成的語言 |
| `tags` | 選填 | 主題標籤，屬於作品本身，不因譯者不同而不同 |
| `category` | 選填 | 分類，屬於作品本身 |
| `excerpt` | 選填 | 作品本身的摘要，一部作品一份，跟每篇譯文自己的 `excerpt`(見 4.2)是不同層級的東西，不衝突同名。目前站上尚未有內容，欄位先開著 |
| `original_publication_date` | 選填 | 原作寫成/首次發表的時間，**不是** `editions[].date`(那是某個特定印刷版本的出版年份，常常是後來的重印，不等於原作寫成時間)。目前站上尚未有內容，欄位先開著;之後若拿來做篩選/排序，空值一律視為「通過」，不因為沒填就被篩掉或當成最小值處理 |
| `editions` | 選填 | 已知來源版本列表，陣列。同一部作品可能同時存在多種語言的來源文本(如日文原文在青空文庫、英譯本在古騰堡)，每項各自記錄一份來源，欄位見下 |

`editions` 每一項的欄位:

| 欄位 | 必填 | 說明 |
|---|---|---|
| `url` | 必填 | 該版本的來源連結。**目前只接受青空文庫、古騰堡計畫這兩個來源**(以及未來可能新增的其他明確來源)的「作品資訊頁」或「本文頁」網址格式，不接受來源不明的其他網址——避免自行認定公版狀態帶來的著作權風險，見翻譯者指南.md 常見問題。build 時會硬性檢查格式，見第 6 節 |
| `language` | 必填 | 該版本文本的語言 |
| `publisher` | 選填 | 出版社/底本 |
| `date` | 選填 | 出版日期 |
| `copyright_status` | 必填 | 該版本文本實際的公版/著作權狀態，自由文字，照實際情況填寫(如「日本公版」「1929年前出版，美國公版」)，不是從固定列舉值挑選——按原文實情記錄，不強制對應到預先定義的分類。與譯文自身授權(全站固定 CC BY-NC-ND 4.0，見 [/LICENSE](../LICENSE))是兩件事 |
| `translator_id` | 選填 | 若該版本本身就是翻譯(如古騰堡的英譯本)，指向 `/content/source-translators/{id}/` |

**不存放**:任何特定中譯所用的細節(那屬於個別 `{uuid}.md` 的 `edition_url`，指向 `editions` 裡的某一項)。

**檔名(可讀前綴)與 `uuid`/`wikidata_id`(欄位)的關係**:檔名只是給人類瀏覽 `content/works/` 時辨識用的提示，不影響任何機制、可以隨時改。`{uuid}.md` 的 `work_id` 引用的是這份檔案內容裡的 `uuid` 欄位值，不是檔名——`work_id` 本身是一個不透明的參照鍵，一旦被引用就不該再改。真正給 build script 打 Wikidata API 用的，是另一個獨立欄位 `wikidata_id`;這個欄位可以獨立修正(比對錯條目等情況)，只改這一個檔案，不牽動任何引用這個 `work_id` 的翻譯檔案。

**給讀者看的作品標題，一律用 `title.zh`，不做語言 fallback**:凡是「這部作品叫什麼」這種給一般讀者辨識用的標題顯示(如全作品列表頁的封面、麵包屑)，直接取 `title.zh`，不會因為沒填就退回顯示日文/英文等原文——顯示讀者看不懂的原文對他們沒有意義，尤其是放大呈現的情況。原文標題只在明確標示「這是原文」的小字場合使用(如 `/works/{id}/` 頁面 H1 上方的小字、`/translations/{uuid}/` 頁面標題上方的小字)，用來源優先序 `ja → en → romaji → zh` 挑選，兩種用途不要混用同一個值。

### 3.3 `/content/source-authors/{可讀前綴}.md`

| 欄位 | 必填 | 說明 |
|---|---|---|
| `uuid` | **必填** | 這位作者真正的識別碼，規則同 3.2 |
| `wikidata_id` | 選填(建議) | 作者的 Wikidata QID，若存在則 build 時自動抓取姓名(多語言)、生卒年、簡介，也是跨檔重複偵測的主要依據 |
| `names` | 有 wikidata_id 則選填，否則必填 | 姓名物件，依語言分 key，例:`{ja: "太宰治"， romaji: "Dazai Osamu"}` |
| `aliases` | 選填 | 其他曾用名/譯名，輔助日後查重比對 |
| `source_url` | 選填 | 來源站(青空文庫/古騰堡)作者頁連結，沒有 `wikidata_id` 時，也是跨檔重複偵測的次要依據(解析出站方作者編號比對，見第 6 節) |

無 Wikidata 條目時，`names`/生卒年/簡介需手動填寫，屬於較少數情況。

### 3.4 `/content/source-translators/{可讀前綴}.md`

| 欄位 | 必填 | 說明 |
|---|---|---|
| `uuid` | **必填** | 這位中間譯者真正的識別碼，規則同 3.2 |
| `names` | 必填 | 姓名 |
| `language` | 必填 | 該譯者的譯入語言(即本站譯文的「來源語言」) |
| `wikidata_id` | 選填 | 若有，也是跨檔重複偵測的主要依據 |
| `source_url` | 選填 | 來源站作者/譯者頁連結，沒有 `wikidata_id` 時，也是跨檔重複偵測的次要依據，規則同 3.3 |

## 4. 譯文檔案規格

歷史上這份檔案曾經叫做「`{uuid}.md`」(檔名嵌 UUID)，本節已改成新規則:檔名純可讀、UUID 移進 frontmatter——文件其他地方若還留有「`{uuid}.md`」的稱呼，指的都是這份「譯文檔案」，不代表檔名真的長那樣，遇到時以本節為準。

### 4.1 路徑與檔名

`/content/translators/{譯者id}/{可讀前綴}.md`

- 檔名只有可讀前綴，不含識別碼，例:`hashire-merosu.md` 或中文譯者直接產生 `奔跑吧梅洛斯.md`——純粹是給人瀏覽自己目錄時辨識用，不影響任何機制，可以事後改名
- 可讀前綴由工具**自動從譯者已經填寫的 `title` 欄位 slugify 產生**，不需要譯者額外輸入
- 真正的身分識別碼是 frontmatter 裡的 `uuid` 欄位(見 4.2)，由 `/tools/new-translation/` 工具或 scaffold 腳本以 `crypto.randomUUID()` 產生，**不需要、也不應該由譯者手動輸入**;`/translations/{uuid}/` 的輸出網址採用這個欄位值，不是檔名，確保網址不會因為譯者事後修改 `title`、重新命名檔案而跟著改變
- 工具自動產生檔名時，建議統一正規化為 Unicode NFC 形式，避免 macOS 與其他系統之間因檔名正規化方式不同(NFD vs NFC)造成 git 誤判檔案異動

### 4.2 Frontmatter 欄位

| 欄位 | 必填 | 型別 | 說明 |
|---|---|---|---|
| `uuid` | **必填** | string | 這篇譯文真正的識別碼，規則同 4.1，一旦發布就不該再改 |
| `work_id` | **必填** | string | 指向某個作品檔案的 `uuid` 欄位值(見 3.2)，不是檔名，build 時驗證存在。作者、原文語言、tags、category 都透過這個反查，不在此重填 |
| `edition_url` | **必填** | string | 這次翻譯實際依據的來源連結。build 時比對 `work.editions[].url`;若沒有對應項目，PR 需一併在該作品的 `editions` 補上這筆來源 |
| `title` | 必填 | string | 這篇譯文自己的標題(可與原作標題不同，是譯者的用詞選擇);同時也是檔名可讀前綴的生成來源 |
| `language` | 選填 | string | 這篇譯文本身寫成的語言。目前站上固定只收中文譯本，實務上用不到，先保留欄位供未來若支援多目標語言時使用 |
| `date` | 必填 | string | 提交日期 |
| `excerpt` | 選填 | string | 手動填寫，索引頁摘要用，不做自動截取 |

`translator` 不列為欄位——由路徑 `/content/translators/{譯者id}/` 推導。`author_id`/`source_translator_id`/`source_language`/`original_language`/`source_publisher`/`source_date`/`source_copyright_status`/`tags`/`category` 都不列為欄位——全部是 `work`(或 `work.editions`)的事實，透過 `work_id` + `edition_url` 反查取得。

`license` **也不列為欄位**:全站譯文授權固定是 CC BY-NC-ND 4.0(見 [/LICENSE](../LICENSE)、[/CONTRIBUTING.md](../CONTRIBUTING.md))，這是專案層級的固定政策，不是逐篇填寫、也不是逐作品查詢的事實。build 產生每篇譯文頁面時直接套用這個固定值，不需要、也不該讓譯者在自己的檔案裡重複打一次同樣的字。

## 5. Build 輸出結構

以下路徑是 build 之後**部署到網站上的公開網址**，跟第 2 節的 repo 原始碼路徑是兩棵獨立的樹——公開網址不帶 `/content/` 前綴(讀者看到的是 `/works/{id}/`，不是 `/content/works/{id}/`)，避免把內部檔案結構外露成公開 URL 的一部分。

```
/translations/{uuid}/index.html                   ← 單篇譯文全文，純靜態，含 canonical，不依賴 JS
/translations.json                                ← 全站譯文 metadata(不含全文)，前端搜尋/篩選用
/works/index.html                                 ← 全作品列表頁(work-level，一部作品一張卡)，見 5.1
/works/{uuid}/index.html                          ← 作品資訊頁:列出此作品在站內的所有譯本(標題摘要+連結)
/tags/{tag}/index.html                            ← 標籤索引頁，摘要+連結
/translators/{譯者id}/index.html                  ← 譯者 profile + 作品列表，{譯者id} 是目錄名稱本身(見 1.1 例外)
/source-authors/{uuid}/index.html                 ← 原作者 profile + 站內譯本列表
/source-translators/{uuid}/index.html             ← 中間譯者 profile + 相關作品列表
```

`{uuid}` 一律取自該檔案內容裡的 `uuid` frontmatter 欄位，不是檔名(見第 3、4 節)。只有 `/translators/{譯者id}/` 是例外，沿用目錄名稱本身當網址片段，理由見 1.1。

**關鍵原則沿用專案規劃.md**:每篇譯文只有一份實體內容(`/translations/{uuid}/`)，其餘所有索引頁(`/works/`、`/tags/`、`/translators/`、`/source-authors/`、`/source-translators/`)都只是「摘要 + 連結列表」，不重複存全文。

### 5.1 `/works/` — 全作品列表頁(work-level)

一部作品一張卡，**不分譯本**——理由:讀者的搜尋意圖是「找一個故事來看」，不是「找某一篇譯文」，同一部作品有好幾個譯本時，列成好幾張長得很像的卡片反而混淆，而且會跟 `/works/{uuid}/`(見 5.2)的功能重疊。這頁只負責「這裡有哪些作品」，選定作品之後要看哪個譯本，交給 5.2 那頁處理。

- 卡片顯示:`title.zh`(封面 + 卡片標題，見 3.2 的顯示標題慣例)、原作者、站內譯本數量(封面右下角小標籤「N 個譯本」，**0 個特別標紅**，方便譯者掃到可認領的作品)
- **尚無譯本的作品也會列出來**，不是只列有翻譯的——這頁同時是「作品目錄」跟「翻譯者尋找認領目標」的入口
- 可篩選欄位:作品標題(文字，partial match)、原作者(文字，partial match)、譯者(文字，partial match;一部作品可能有多位譯者，任一位符合就算)、分類(下拉)、原文語言(下拉)、標籤(checkbox 多選，可複選)
- 篩選邏輯**完全在瀏覽器端跑**:build 時所有卡片已經連同 `data-*` 屬性完整輸出到 HTML 裡，`assets/js/works-filter.js` 只是讀這些屬性做比對、切換顯示/隱藏，沒有 JS 一樣能看到完整未篩選清單
- 首頁的搜尋框(純文字，見 homepage.js)導向 `/works/?q=...`，這頁的 JS 讀網址參數自動預填並套用

### 5.2 `/works/{uuid}/` — 資訊卡頁(對應青空「card」頁 / 古騰堡「ebooks」頁)

顯示「這部原作」本身的資訊，不含任何譯文全文:

- 作品標題(原文標題 + 站內各譯本各自取的標題)
- 原作者:連結 `/source-authors/{uuid}/`，帶顯示姓名/生卒年摘要
- 原文語言(`original_language`)、tags、category
- 已知來源版本(`editions`):每項顯示語言、出版資訊、版權狀態——同一部作品可能同時有多種語言的來源(如日文原文 + 英譯本)，各版本狀態可能不同，並列顯示，不取單一值蓋過去
- **站內所有譯本列表**:每個譯本一行，顯示譯者(連結 `/translators/`)、依 `edition_url` 對應到的 `editions` 項目取得語言(若該項目有 `translator_id` 則一併連結中間譯者)、`excerpt`、連結到對應的 `/translations/{uuid}/`

這一頁存在的理由，就是讓「同一部作品的多個譯本」有地方被同時看見、互相比較——這是本站跟青空/古騰堡最大的結構差異(它們不會同時收多個競爭譯本)。

### 5.3 `/translations/{uuid}/` — 內容頁

進入即直接是這篇譯文的正文，不重複作品頁上的完整 metadata。仍保留最小必要的頭尾資訊，呼應青空/古騰堡內容頁「底部放底本資訊區塊」的慣例:

- 頁首:標題、譯者連結、回作品頁連結
- 正文:全文
- 頁尾(精簡版引用區塊，非完整 metadata):`edition_url`、`license`、原作者連結、canonical link

頁尾這幾項是「引用」不是「資料重複」——完整的作品層資訊只存在 `/works/{uuid}/`，這裡只放讀者當下讀這篇譯文就需要知道的最小引用資訊。

## 6. 驗證規則(build-time / CI)

**目前的執行時機**:以下檢查目前是 `build.js` 的一部分，實際只在 Cloudflare 部署時(即 merge 進 `main` 之後)執行，PR 階段還沒有另外接一支會在 merge 前擋錯誤的 GitHub Actions——也就是說，PR 通過與否目前純粹取決於是否有人去看，不是自動化把關。要讓「自動檢查通過即可合併」這個政策(見[專案規劃.md](./專案規劃.md)、[翻譯者指南.md](./翻譯者指南.md#8-自動檢查))名副其實，需要另外設一支在 `pull_request` 事件上執行 `node build.js`(或抽出其中驗證邏輯)的 workflow，並設成必要的 status check——這件事尚未做，列在第 7 節開放項目。

- **`uuid` 唯一性檢查**:同一類別(works / source-authors / source-translators / 全站譯文)內，`uuid` 欄位值不得重複——這是最基本的資料完整性要求，重複代表複製檔案時忘記重新產生 uuid。
- **參照完整性檢查**:譯文檔案的 `work_id` 若在 `/content/works/` 全部檔案的 `uuid` 欄位裡找不到相符值，build 直接失敗;`work.author_id` 若在 `/content/source-authors/` 找不到相符 `uuid`，同樣失敗;`editions[].translator_id`(若有填)在 `/content/source-translators/` 找不到相符 `uuid` 也失敗。等同於用 build script 充當資料庫外鍵約束，只是查找依據從「檔名/目錄路徑」改成「掃描全部檔案、比對 `uuid` 欄位值」。
- **來源比對檢查**:譯文檔案的 `edition_url` 應能在對應 `work.editions[].url` 中找到相符項目;找不到時 build 失敗，提示需在該作品的 `editions` 補上這筆來源，而不是放任一筆孤立、未登記的來源存在。
- **來源網址格式檢查**:`editions[].url` 必須符合青空文庫、古騰堡計畫其中一種已知的「作品資訊頁」或「本文頁」網址格式(見 3.2)，不符合則 build 失敗——這是真正的把關，workshop 表單上的 `pattern` 屬性只是前端先擋一次，不透過工具、直接手動編輯檔案送 PR 的人還是會在這裡被擋下來。
- **Wikidata 抓取**:build 時依 `wikidata_id` 呼叫 API 抓取姓名/生卒年/簡介等內容並快取進輸出頁面;抓取失敗時 fallback 到 description.md 中手動填寫的欄位(若無則顯示 ID 本身，不擋 build)。
- **跨檔重複偵測(works / source-authors / source-translators 各自類別內比對，**會直接擋 build 失敗**)**:
  1. **`wikidata_id` 相同** → 同一類別內，若兩個不同檔案(不同 `uuid`)填了同一個 `wikidata_id`，判定重複，build 失敗
  2. **站方編號相同**:沒有 `wikidata_id` 可比對時，退而從 `editions[].url`(works)或 `source_url`(source-authors/source-translators)解析青空文庫/古騰堡網址裡的站方編號比對，同一類別內編號相同也判定重複，build 失敗。青空文庫「作品資訊頁」(`cards/{author}/card{work}.html`)、「本文頁」(`cards/{author}/files/{work}_xxxxx.html`)、「作者資訊頁」(`index_pages/person{N}.html`)，古騰堡「作品資訊頁」(`ebooks/{N}`)、「本文頁」(`cache/epub/{N}/...`)、「作者資訊頁」(`ebooks/author/{N}`)六種格式都已涵蓋——同一部作品的資訊頁跟本文頁用的是同一個編號，解析後比對編號，不是比對網址字串本身
  3. 兩者都沒有 → 無法自動判斷，依賴 `/tools/new-translation/` 的搜尋功能與事後的社群巡邏彌補，見 1.2、7

  這一層之所以直接擋 build，不是只留警告，是因為現行「自動檢查通過即可合併」的政策下沒有保證會有人另外去看警告訊息——精確 ID 相同這件事本身也夠可靠(不像下面的模糊姓名相似度需要人工判斷)，擋下來不會有明顯的誤判風險。
- **新增條目相似度檢查(lint，非阻擋性，跟上面的「跨檔重複偵測」不同)**:上面比對的是精確的 ID 值是否相同;這裡指的是完全沒有任何外部 ID 可比對時，單純比對 `names`/`aliases` 文字的模糊相似度。**目前先不做**——比精確 ID 比對複雜得多(門檻、演算法都要另外設計)，先記錄在此，等實際發生「兩邊都沒填外部 ID 導致的重複」問題再評估。

## 8. 部署

**上線網址**:https://publictranslationwebsite.shell-prisoner.workers.dev/

**託管方式**:Cloudflare 現行的專案建立流程走的是 **Workers(靜態資源)**，不是舊版 classic Pages 的「git 整合 + build command + output directory」三欄位介面，而是 **Build command + Deploy command** 兩欄位，輸出目錄改在 `wrangler.toml` 裡設定。實際效果跟 `專案規劃.md` 原本規劃的「push 即自動觸發 build + 部署，不需要另外寫 GitHub Actions」一致，只是 Cloudflare 這邊的產品/介面名稱從「Pages」變成「Workers 靜態資源」——純粹是 Cloudflare 自己的產品演進，build 出來的仍然是純靜態檔案，沒有用到 Workers 的動態執行邏輯或 KV，不違反「避免用到 Cloudflare Workers/KV」的原則。

**設定內容**(Cloudflare Dashboard → 該 Workers 專案 → Build configuration，這些是**只存在 Dashboard 裡、沒有進版控**的設定，重新建立專案時要照這裡手動填回去):

- Root directory:`/`
- Build command:`npm install && cd scripts && npm install && node build.js`
- Deploy command:`npx wrangler deploy`
- Version command:`npx wrangler versions upload`
- Branch control:Production branch 設為 `main`;「Builds for non-production branches」有勾選，代表 push 到任何分支都會觸發一次 build(非 `main` 分支會是 preview 部署，不影響正式網址)
- Build watch paths:
  - Include:`content/**`、`scripts/**`、`assets/**`、`wrangler.toml`、`package.json`、`package-lock.json`
  - Exclude:`node_modules/**`、`.git/`
  - 意味著**只改 `docs/`、`CONTRIBUTING.md`、`LICENSE` 這類不影響 build 輸出的檔案不會觸發重新部署**(本來就不需要，因為這些檔案不參與 `dist/` 的產生)

**相關檔案**(這些有進版控，重建專案時不用重填，repo 裡就有):
- `/wrangler.toml`——宣告 `[assets] directory = "dist"`
- `/package.json`——根目錄的 devDependency，釘住 `wrangler` 版本(避免每次 deploy 都重新解析版本、行為漂移)
- `/scripts/package.json`——build script 自己的依賴(gray-matter、markdown-it)

**目前狀態**:2026-08-14 起先移除 Cloudflare 上的 Worker 專案，暫時不公開上線(原因見翻譯者指南/CI 尚未補齊，不想讓未完成流程被外部看到)。之後要重新上線時，回 Cloudflare 建一個新 Workers 專案，照上面「設定內容」原樣填一次即可，不需要改動 repo 裡任何檔案。

**GitHub Pages 備援**:尚未設定，見第 7 節開放項目。
